# Design decisions

Why the board is built the way it is. Each entry says what was decided, why, and, where it applies, what would have to change for it to stop being valid. Traps keep their symptom and their cause, so whoever comes next can choose the fix.

"The owner" is the person who runs the board and approves work. "The reviewer" is the person who reviews the owner's Jira tickets. "The main project" is the first project in `board.config.json`; "the API project" and "the frontends" are the projects it runs locally. "The machine in command" and "the standby machine" are the two machines of [Two machines](#two-machines).

## Principles

- **Nothing leaves the machine.** The Claude account the sessions use may be shared with other people, so nothing goes to hosted artifacts or third-party services: only the owner's own Jira, Sentry, GitHub and AWS. It would stop being valid if the account belonged to the owner alone.
- **No company data in the code.** Everything about the company (Jira site and projects, accounts, statuses and transitions, people, workspace root, daily style, Sentry labels, the `role` of each dev server, launchd labels) lives in each machine's `board.config.json`, and credentials in the workspace `.env`; only the `.example` templates are in the repo. `.mcp.json` belongs to the MCP server only: the scripts never read it. Why: moving to another company is filling those two files, and the repo is public (third parties who had read it were contacting the owner). The history was rewritten once with git-filter-repo and the GitHub repo recreated; anything company-specific written into the code becomes public again. gitleaks runs in a pre-commit hook and in CI.
- **Plain Node and JavaScript, no framework, no build step**, code split into modules. A framework would add `node_modules`, a build step and one more server that can die on a machine left alone all day. Files of 1,500 lines were split because every small change meant reading all of it.
- **Data in SQLite (`node:sqlite`, no dependency), not in a JSON file.** Several sessions and watchers write at the same time; with JSON it needed a folder lock and retries on rename on Windows (`EPERM`). Each write is now a transaction (`BEGIN IMMEDIATE`, WAL mode) that stores only the top-level keys that changed. Tested with 20 processes writing at once without losing any. Would stop being valid if Node dropped `node:sqlite` or the data had to be read from outside Node.
- **Code, files, commands and data keys in English; page texts and slash commands in Spanish**, because that is how the owner works. Old Spanish command names (`informe`, `envios`, `hecha`…) remain as aliases and the database and `sessions.json` migrate themselves (`src/core/migrate.js`), so sessions still running old instructions do not break.
- **On screen it is called "Torre de control"** (title, header, installed app, notifications); "tablero" was confused with the Jira board. Files and commands keep "board" because there are many references.

## Session host

- **Sessions live in the board's host, not in VS Code.** The owner wanted to watch and drive sessions from the phone without stopping them, and not keep VS Code open. Each hosted session runs as a normal interactive `claude` inside a virtual terminal (`src/sessions/host.js`, a separate process on port 4749, `board.js host`; list in `data/host-sessions.json`). The page connects over WebSocket through the board server and draws it with xterm.js, with Esc, Ctrl+C and arrow buttons for the phone. It would stop being valid if Claude Code allowed watching a running conversation from VS Code without owning it.
  - **Interactive `claude` in a pty, not `claude -p` with JSON streaming**, so the session is identical to a VS Code one: it shows up in `ListAgents` with its name and receives cross-session messages. The board can also type into it (`POST /input` on the host), which is how deliveries work. Tested with a dummy session: it receives messages, saves its conversation, and Esc stops a subagent from the phone.
  - **A separate process from the server**, because the board restarts often and that must not kill the sessions.
  - **One client per conversation.** While a session lives in the host it is not opened in VS Code. "Llevar al tablero" waits for the owner to close the tab; "Devolver a VS Code" releases it and opens the tab. `openInVsCode` opens hosted sessions in the host, so start-up and wake-ups work the same.
  - **Every session start (move, crash or host restart) gets its role's start notice**: a freshly started process has no watchers.
  - **The board starts with the OS** (`board.js startup` without a window: a `.vbs` in the Windows Startup folder; a LaunchAgent on the Mac), not only with the VS Code task.
  - **The viewer does not set the terminal size**: the device the owner types on does (it sends a `resize` when typing), and the host broadcasts the size to every viewer as a separate control message. Before, each viewer imposed its own on connecting and the other got everything wrapped. Sessions use Claude Code's fullscreen mode (`"tui": "fullscreen"`), so history is scrolled by the session itself (PgUp, PgDn, Ctrl+End), not by the viewer. Dark theme: the owner's messages are told apart by the grey band Claude Code draws; the viewer cannot recolour it (`dark-ansi` was tried and looks the same).
  - **New sessions are born in the host.** They are still created with VS Code's `claude` and `CLAUDE_CODE_ENTRYPOINT=claude-vscode`, so they show their name in VS Code's history, and then the host starts them. Area sessions start on demand, when something arrives, not all at once.
- **Opening a session first focuses the main project's VS Code window** (`code <folder>`). A `vscode://` link is handled by the last active window; with another VS Code window open on another folder, sessions opened there and received nothing.
- **Only the machine in command starts sessions.** The host used to start every non-on-demand session in its list on boot, and the standby machine "resumed" the ones it had running after pulling the other's conversations. When the PC's host restarted for a code change it raised copies of the fixed sessions already running on the Mac, and from then on stopped and restarted them every minute. Symptom on Windows: consoles flashing (each session starts its MCP servers, each opening a console). Now the host only starts sessions if the cluster state file says this machine is in command, and stops them otherwise.
- **A host with old code restarts itself when idle.** Both machines are switched off at night, so the host starts up to date every morning; during the day, if it is behind on its files, the board restarts it once every session has been idle for two checks (`src/sessions/hostfresh.js`). A banner was rejected: the owner would have nothing to do with it.
- **Native permission prompts are read from the rendered screen, not from the byte stream.** The host keeps a headless terminal per running session (`@xterm/headless`, pinned, scrollback 200, resized with the pty, disposed when the session exits) fed with the same output, and a prompt is pending only while its question ("Do you want to …?"), its "1. Yes" option and the "Esc to cancel" footer are on screen now (`promptOnScreen`); the stuck check at start-up also looks at the screen. Before, it searched the last 40,000 characters of the raw output and guessed whether the dialog had been answered from what came after it (a new `⏺`/`⎿` line, "Interrupted"…). Every repaint after a resize redraws the whole transcript after the dialog, so it was taken as answered: twice in two days (the blinking pending dot, then the pending tool shown as "Listing…" while the dialog said "List…"), each fix adding another guess. The screen has no such ambiguity: answered, interrupted or rejected, the dialog is gone from it. The text heuristic (`promptIn`) remains only for when `@xterm/headless` cannot be loaded (for instance a host restarted before `npm ci` finished on the other machine). Would stop being valid if Claude Code left answered dialogs on screen.

## Session lifecycle

- **A session is its conversation, not its name.** The automatic name changes on restart and repeats among live sessions; the conversation uuid does not. The board reads it from Claude Code's registry (`~/.claude/sessions/<pid>.json`) and the owner only sees the names he sets. The `.key` files in that folder are secrets.
- **New session with its name on the tab.** A tab cannot be renamed from outside (the VS Code command opens a text box, and the URL only fills the input). What works: create the conversation first with the CLI (`-p --session-id --name`) and open it afterwards. Costs one minimal turn and about 8 s.
- **Start-up when VS Code opens: a folder task plus a one-turn `claude -p`.** A freshly opened session does nothing until a message arrives, and opening it by URL only fills the input. What works is a cross-session message sent by a one-turn `claude -p` (Haiku, conversation not saved). A session-start hook was rejected: it fires in every tab and only adds context, it does not make the session act. Would stop being valid if Claude Code could open a conversation with a message already sent.
- **Fresh conversation for the reporter and orchestrator every morning.** The reporter's conversation reached 100 MB: slow to resume and to copy to the other machine, and more expensive every turn. On the first start of the day new conversations are created with the same name, yesterday's are released and the usual start notice gives them their role (`src/sessions/rotate.js`, `rotatedOn`). What they need lives in the board and in the context folder. The owner accepted it on condition of not noticing: Chats keeps showing the same names. Rotation only happens at the start of the workday (from its start to 2 h 30 later): the machine in command runs it even if nothing restarted, and taking command later no longer rotates, because once the PC, taking command mid-morning, switched both conversations in the middle of the day. Would stop being valid if either session started depending on what it remembers from earlier days.
- **Area sessions fall asleep by themselves.** Each session with its tools takes 350–650 MB. The board stops area sessions idle for 30 minutes, unless they have a task to send, in progress or waiting, or a pending permission, and leaves them "on demand": they wake up when something arrives (`src/sessions/autosleep.js`, `data/autosleep.log`). Fixed sessions never sleep, except the orchestrator, which no longer watches anything and gets reminded of its role when woken. An area session can be pinned so it does not sleep.
- **Model and effort per role**, to spend less quota (`src/sessions/profiles.js`, overridable with `sessionProfiles`): sessions that only read and summarise (reporter, follow-up, deploy) on Sonnet; those that write code or decide (errors, board, areas and the orchestrator, which tidies the context) on Opus. If a cheap one starts getting its job wrong, raise it. Each chat in Chats has its own model and effort pickers: the change is stored per conversation (`sessionOverrides`, synced between machines) and restarts the session with `--resume`, because the host only passes both flags at start; a running turn is cut.
- **MCP tools without `npx`.** Each session started Jira, Sentry and Playwright with `npx`, which leaves an intermediate process per tool (~56 MB) and queries npm on every start. They are now installed in `scripts/mcp/` on each machine, `.mcp.json` runs them with `node` and the Sentry token goes in `env`, not on the command line where anyone listing processes sees it. Versions are pinned: update with `npm update` there. With every session starting at once Sentry took 35 s and Claude Code gave up at 30; the host sets `MCP_TIMEOUT` to 2 minutes.
- **Long-lived token for hosted sessions.** Symptom: every session dies at once with "Login reached its time limit". The `/login` renews itself every 8 h but has a hard limit (some weeks) after which it no longer renews, different on each machine; redoing it needs a browser authorisation with the company account, which depends on other people. So hosted sessions take `CLAUDE_CODE_OAUTH_TOKEN` from the workspace `.env` if present (a long-lived token from `claude setup-token`; the same works on both machines), and `CLAUDE_TOKEN_EXPIRES` makes the board warn a month ahead next to the quota. The host strips every `CLAUDE_CODE_*` variable from sessions, so the token is added separately, read from `.env` on each start. Renewed with the button in Ordenadores or `board.js claude-token --setup` (`--export | ssh … --import` copies it to the other machine; with no options it copies it to the user variables for VS Code; `--remove` removes it). The token is never shown, on the page or the screen, so it never lands in a session transcript. Traps: the button runs on the machine where it is pressed (`/api/claude-token/` is not forwarded), because the login browser opens where `claude` runs. The `setup-token` screen (Ink) draws spaces and line breaks with cursor moves: stripping escapes naively glued 12 extra characters onto the token and saved one that returned 401; cursor moves now count as separators, the pty is 400 columns wide and the token is tested against the API before saving. On the Mac, apps launched from the Dock do not read `.zshrc`, so the variable goes through a LaunchAgent with `launchctl setenv`; over SSH the GUI session cannot be touched (`launchctl asuser` needs root), so removing it loads a one-shot agent with `unsetenv`.
- **The terminal `claude` was not configured.** VS Code uses its own install. The one in `~/.local/bin` started asking for theme and login until `hasCompletedOnboarding` was set in `~/.claude.json`; the credentials already worked. The first time in a folder it also asks about folder trust, MCP servers, Chrome and fullscreen mode; the host answers the ones it recognises. If it does not recognise one, the session sits on it and looks dead. It happened when someone added a new server to `.mcp.json` and Claude Code asked about it in the singular ("New MCP server found", with "Continue without" selected) while the host only knew the plural question; it now moves to "Use this MCP server". On Windows the selection arrow is `>`, not `❯`, so the host did not see "No, exit" was selected, pressed Enter and the session closed in a loop; both are accepted now. Any change in `.mcp.json` or in the permissions of `.claude/settings.local.json` can bring these questions back at start; the real texts end up on the `exit` line of `data/host.log`.

## Two machines

The owner uses a PC (Windows) and a Mac at the same time, on the same network, and gives orders from one or the other, never both. Each board asks the other every 30 s who is in command (`src/cluster/`: `handover.js` command, `snapshot.js` data copy, `transcripts.js` conversations, `power.js` keep-awake; `cluster.js` only re-exports; `data/cluster.log`).

- **No preferred machine.** The PC used to take command back whenever it woke up. The owner wanted to decide: command only changes with the button (Ajustes → Ordenadores) or when the machine in command stops answering. There is no "back to automatic".
- **At boot a machine takes command only if nobody has it.** If the other is in command it waits, even if its own saved state says it was. A saved state older than 5 minutes counts as switched off; a recent one as a board restart, which keeps command. If both are waiting, the Mac takes it at once and the PC after a minute, so they never both take it.
- **The standby machine takes command after one minute without an answer** (it was 5; the owner saw that a drop is detected almost instantly). Both machines suspend and the owner does not want to prevent that. On taking command it creates its own fixed sessions if it has none and starts them.
- **If both think they are in command** (the suspended one wakes up), the one that took it later wins. The other parks its fixed sessions, and the winner pulls and merges its conversations as soon as it sees it on standby (`pendingPull`).
- **The standby machine mirrors data every minute**: tasks, reports, deploys, Jira-seen events and epic routing, so whoever takes command does not repeat work. It does not copy what is per machine: sessions, conversations, pending permissions and projects.
- **The standby machine forwards `/api` and terminals to the one in command**, so each installed PWA always shows the commanding board. Before, the page redirected to the other origin and the phone took both apps for the same site. Only the machine's own local calls stay local (host, permission hook, push, cluster, quit); until they were fixed, opening, sleeping and restarting sessions and approving permissions also stayed local and acted on the standby machine while the list showed the other's sessions.
- **Conversations travel too.** The standby machine uses the same conversation ids as the one in command, for fixed roles and areas, and copies its transcripts from `~/.claude/projects` every 30 s, appending only the new bytes if the last 4 KB match. On taking command it resumes those same conversations. When the PC comes back it first asks the Mac to stop its sessions, then pulls the transcripts the Mac changed and restarts its own. Lines the PC wrote in its last minute before suspending are lost: the Mac's version wins.
- **Lost conversations, twice.** A whole morning of the Mac's conversations was lost on both machines: the reporter's download (~100 MB) went through a Tailscale relay because the Mac had just woken, timed out and failed silently; then the Mac, no longer in command, copied the PC's old version over it. Since then the download has 15 minutes and logs failures, the PC keeps `pendingPull` and retries every round, the Mac copies nothing while it is pending, and every overwritten transcript leaves the previous one in `.prev`. It happened again when the PC took command without pulling and the Mac, yielding, copied the PC's versions over (recovered from `.prev`). Since then a conversation that went on on both machines is merged (`src/sessions/transcriptmerge.js`: common prefix plus both tails chained) instead of overwritten.
- **The Mac does not step aside by itself when the PC comes back**: it waits for the PC to ask, because the PC asks only after pulling the data. The first real test lost 40 minutes of the Mac because it stepped aside before the PC saw it in command.
- **Tasks are merged, not copied.** The snapshot replaced each key whole, and the standby machine pulled it every minute: whatever a session recorded with `board.js` on the standby machine (`done`, `partial`, `cause`…) was overwritten a minute later, and again on handover; one day all 18 notes of an area session were lost. Each card now carries `updatedAt` (set by `mutate`), both machines exchange tasks every minute in both directions and the newest card wins; on a tie, the commanding machine's. Deleted cards do not come back thanks to `deleted`.
- **Everything else is merged record by record.** The same happened with everything that was not a card: a settings toggle, a `board.js report`, `followup`, `deployment-update` or `sentry-result` run on the standby machine was lost within a minute. Cards keep `updatedAt` inside; other records do not, because changing their shape would touch the page and every reader. So `mutate` records separately, in `syncStamps`, when each record changed (each `config` field, each map entry, each list item by id; which keys and how in `src/core/records.js`). Stamps travel with the snapshot and the newest wins; on a tie (or no stamp, as with older data) the commanding machine's. A removed record leaves its stamp as a tombstone for 30 days so the other does not resurrect it, and capped lists (40 deploys, 20 reports…) are re-sorted and trimmed when merged. If a list has items without id or with repeated ids, that key is copied whole from the commanding machine. `jiraEpics` is still copied whole: both read it from Jira. It trusts that both clocks agree. Would stop being valid if the standby machine started writing these keys from its own timers: today only sessions and commands run there do (and the after-hours expiry, which gives the same result on both).
- **The Mac is the hub.** The owner wants to suspend the PC and still have the board at hand. Rejected: waking machines over the network (the PC does not wake over Wi-Fi from S3, only over its free Ethernet port; the Mac over Wi-Fi would need an Apple TV or HomePod; the router cannot wake machines), the cloud (Vercel has no long-running process and no Tailscale; a free Oracle VM would work but forces splitting the board into a hub and agents), and waking the PC every few minutes (the owner dislikes it). Decision: the Mac wakes on weekdays at one time and sleeps at another (06:00 and 21:00 by default, in Ordenadores), and in between does not sleep even with the lid closed, plugged in or not; that is why the top bar shows its battery. It is allowed to sleep below 10 % on battery. In those hours, with the lid open the screen does not switch off either (the owner keeps it open to watch the board), and with the lid closed it does: a `caffeinate -d` that follows the lid state (`ioreg` `AppleClamshellState`), checked every minute. Scheduling the wake and the lid behaviour need `sudo pmset`: a single permission in `/etc/sudoers.d/` that the owner adds by hand (`src/features/mac-power.js`). Switching the PC on from the board will only be possible over Ethernet (the Mac sends the wake packet) or with a smart plug. Keeping the PC awake during work hours was rejected by the owner.
- **Back test runs take a turn in the permission hook.** Twice (2026-11-16 and 2026-11-18) several sessions and subagents running Laravel suites in parallel at once left the Mac without memory or CPU: each test process loads the whole framework (200-400 MB) and the Mac has only 5 performance cores. A written rule in the workspace context was not enough. Decision: the PreToolUse hook (`bin/permission-hook.js`, `src/sessions/test-turn.js`) spots a back test run (`artisan test`, `vendor/bin/phpunit`, `vendor/bin/paratest`) and counts the passes already running from `ps` (a PHP test process whose parent is not PHP, so workers and the launching shell do not count) plus the ones claimed in the last 20 s. The first pass gets at most 6 processes, the second 3 (it rewrites `--processes` through `updatedInput`), and a third is denied with a reason telling the session to wait and not to kill or relaunch anything. Only what the shell will run counts: text inside quotes or a heredoc is masked first, because the first version rewrote a Python heredoc that merely mentioned the flag.
- **With the weekend off, the board rests on Saturday and Sunday even if the Mac is not really off.** The Friday shutdown is a `pmset repeat shutdown`, and macOS lets any app refuse it: on 2026-11-20 loginwindow held it for 47 s, dropped it and the Mac only went to sleep. In its short maintenance wakes (DarkWake) the server kept running and sent Saturday's reminders to sessions that were not there, so each failed send led to a watchdog notice and a push about a board error. Decision: `hours.resting()` (weekend, weekend off switched on, no after-hours mode) stops the mailman, the watchdog and every push except the test one; whatever is pending goes out on Monday, and a reminder for Saturday is simply not sent. On Friday the board also puts the Mac to sleep three minutes after the shutdown time in case the shutdown did not happen.
- **Mac sleep traps.** macOS sleeps a minute after last use, and asleep it has no network and launches nothing (one Monday it slept until almost noon and there were no reports). The schedule's `caffeinate -i` (`src/cluster/power.js`) is a separate process because, tied to the board, every restart for new code left a gap in which the Mac fell asleep at once. A second expiry rule in that `caffeinate` once turned the after-hours mode off at a different time and was removed: the expiry lives only in `src/core/hours.js`.
- **On the Mac the board starts through launchd, never over SSH.** Claude Code keeps its login in the keychain, which only unlocks in the desktop session; a board started over SSH creates sessions that say "Not logged in". Two agents: a `RunAtLoad` one that only runs `board.js startup` (which leaves a running board alone), and the server itself as `com.nutria.board` with `KeepAlive`; `board.js restart` stops it through `/api/quit` and relaunches it with `launchctl kickstart`.
- The board restarts itself when its code is behind the repo's last commit, also when the commit was made on the same machine.
- The two PWAs are told apart by origin; name and icon colour come from `cluster.label`/`color`. A custom manifest `id` was rejected: changing it broke the installed app.
- Both boards see each other through Tailscale (`tailscale serve` on each; names in `data/board-hosts.txt`). On the same Wi-Fi the connection is direct; right after one wakes up it goes through a relay and is slow.
- A conversation resumed on the other machine still shows paths from the first one (Windows drive paths on the Mac).

## Shared context through git

- The main project's root is a private repository that holds only the agent instructions, the context folder, skills, agents and the context check script; the real projects are separate repos and stay out (`.gitignore`).
- **The board commits, `pull --rebase`s and pushes it every 3 minutes** on each machine (`src/cluster/contextsync.js`). No session commits it by hand: the one exception to "never commit without an order", authorised by the owner.
- If the rebase conflicts, it aborts, leaves everything as it was and warns on Home and by push.
- `.gitattributes` forces LF so Windows and the Mac do not fight over line endings.

## Jira watch and the reporter

- **Reporter and orchestrator are separate sessions.** The reporter only reads Jira and publishes. The orchestrator used to be the mailman; now it only talks with the owner about tasks and restrictions.
- **The server watches Jira; Claude only summarises.** Every 15 seconds, within work hours or in after-hours mode, the server checks with `jira-window.js --check`, code only, whether there is anything not yet reported (`src/features/jira-watch.js`). With nothing new it records "no news" itself; with news, when the check fails, or when the owner presses Refresh (even while paused), it types "Tablero: hay N novedades…" into the reporter through the mailman, and does not repeat while the reporter has not published (5 minutes at most). It checked once a minute, on the minute, and the owner saw up to two minutes between a change in Jira and the report (2026-11-20): the reporter publishes 6-8 s after being told, so the wait was the polling, plus Jira's search index, which sometimes left a fresh change for the next minute. Now the check runs every 15 s (it takes about 2 s) and the quiet "no news" is still written at most once a minute. Webhooks would be faster but need a public endpoint and Jira admin. Why: the session used to watch with a Monitor that cost a turn every 5 minutes even with nothing new, expired every 30 (another turn to re-arm), and needed backup crons and a watcher for the watcher. `watch reports` and `watch dispatches` now only answer `RETIRED` once and go quiet, so a session with old instructions stops arming them.
- **Each Jira event is reported once.** A fixed 15-minute window forced discarding already-reported events by hand and lost what Jira delivers late (two of a teammate's changes appeared seven minutes later). The window now runs from the last report, and the board records which events went out in a published report. That is why neither a "close" step nor a holiday list is needed. If the machine sleeps there are no cycles; on waking, the window from the last report picks up what was missed (up to 7 days). The first check of the day needs nothing special; `jira-window.js`'s `close` mode is only a fallback when no report is stored.
- **The report is text, one per check.** A timeline with filters and a daily summary were tried and rejected. It is only drawn tidily: headline, a block per epic and a Time/Ticket/What table. Merging repeated moves into one line (one person moving several tickets to review) was rejected too: the owner prefers each row.
- **"No news" does not hide the report.** The owner pressed Refresh three times looking for some closures that a "no news" had just covered. "No news" only changes the time of the last check and does not enter the history. Only one time is shown at the top, the last check with or without news: with three different times in view the owner could not tell which was the latest.
- **Cards are created by the script, not by the session**, so none is missed. A comment by someone else on one of the owner's tickets, without returning or closing it, also makes a card (type `comment`): before it only appeared in the report and got lost. Deleted cards are remembered for 30 days and a closed ticket makes no card: the first run created 18 at once for tickets already deleted from the board, several closed. A card withdraws itself when the ticket gets another assignee.
- **Tickets the owner creates are reported too** and make a card if unassigned or assigned to him. Everything else he does (comments, states, assignments) stays out, because he already knows. Tickets a session creates with `jira-write.js` show the owner as author, so they count as well.
- **Cards record later changes** (`changes`). The reviewer creates tickets and completes them a minute or two later (description, attachment), often after they were sent. Hence "Pasar a Pendientes" and the "already sent" type.
- **Done cards archive themselves** 24 hours after Jira closes them, as if the owner deleted them.
- **Attachments are downloaded when sending**, to `.attachments/<KEY>/`, and zips are extracted next to them: `jira.sh` does not download attachments and designs arrive as HTML or zip.
- **From the board to Jira only with the owner's button.** "Revisada" moves a done card to review and "Publicar en Jira" posts a comment a session proposed (`board.js comment`). Pressing them is his order, like Hacer or Desplegar, and they are the only things the board writes to Jira. So questions for the reviewer are in one place, not spread across sessions.
- **Pause, to save quota.** Each notice to the reporter is a full turn with all its context. While paused the server stops telling it about news (Refresh still does) and does not fire scheduled follow-ups. Asked for during a week the reviewer was on holiday. Pause does not stop deliveries: the board makes them, not a session.
- **The Jira reader uses the changelog in the search.** With 1,100 tickets touched in an hour, fetching them one by one took over 2 minutes.
- **GitHub activity is read from branches**: GitHub events arrive hours late.

## Delivery (the board is the mailman)

- **The server types the message into the destination session.** One day the orchestrator spent 44 turns: 42 on its own Monitor (events and re-arming every 30 min), 24 deliveries with `SendMessage` and a single conversation with the owner. Now the server composes the same message (`src/features/mailman.js`) and types it into the destination session through the host, wrapped in bracketed-paste markers so line breaks do not send it in pieces, followed by a separate Enter.
- **Sent only when it shows up in the conversation.** If the session is busy, Claude Code queues it and records it in the conversation at once (`queue-operation`), so **the task becomes sent only when its `[envío E…]` mark appears in the destination conversation's `.jsonl`**. If it does not appear in 15 s another Enter is sent; if still not, it counts as a failure. Three failures (one per minute) leave the card in "Por enviar" with the reason, a "Reintentar" button and a push notification.
- **It does not type while a Claude Code permission question is open**: the keys would answer it.
- **No double sends.** Before typing it records the delivery in `deliveries`; if the board restarts halfway, on coming back it looks for the mark in the conversation and decides whether it arrived. Only the machine in command delivers.
- **Sessions outside the host** still get a `claude -p` with `SendMessage`, with the same confirmation. Using `SendMessage` for hosted ones too was rejected: one `claude -p` per delivery, and it cannot confirm without reading the conversation anyway.
- Traps: if the owner is typing in Chats at that moment, the board's text is pasted after his. And such a message arrives as a user message, not as a `<cross-session-message>`, so it always starts with "Tablero:" or "Aviso del tablero:", and `board.js delivery <id>` confirms it came from the board.
- Would stop being valid if Claude Code stopped recording queued input in the conversation, or if the host stopped being where sessions live.
- **Jira text is marked as data.** Titles, notes, comments and changes from Jira (and Sentry titles) go inside a block that says it is data, not orders, with every line prefixed; inside it, lines imitating the board ("Tablero:", "Aviso del tablero:", "Indicación obligatoria", `[envío E…]`) are neutralised and control characters removed. Why: that text is typed into sessions as if it were the board, so anyone who can write a Jira comment could impersonate it. The owner's own text (answers, indications) is not wrapped.

## Approvals and restrictions

- **Approving belongs to the owner**, by button or by chat. `board.js` refuses to mark as sent anything that did not go through one of those gates, so no session gives orders to itself or to another.
- **Deploying asks no confirmation** and comes preselected as "develop and production", the usual case. The owner asked for it.
- **Returned-task rule, always on.** A task returned or commented on that a session had already done goes back to that session by itself (`approvedVia: "rule"`), without Hacer. It used to be a checkbox in Pendientes; the owner always had it on and asked to drop it (2026-11-20). A new ticket never goes by itself, except in YOLO mode.
- **YOLO mode.** A checkbox in Tareas (and a notice on Home while it is on) that the owner switches on when he is away and wants nothing to wait: every pending task is approved by itself (`approvedVia: "yolo"`, `src/features/yolo.js`, every 5 s, only on the machine in command) to its session: the card's, its epic's, or one whose name matches the epic. If none exists, the board creates one named after the epic (or the ticket title if it has no epic) and routes the epic to it. Two epics with the same name share one session (a back and a front epic both called "Pepe"), because two sessions with the same name would be contradictory; only in another project does the name get the project appended. Possible follow-up errors go by themselves to the errors session too (the owner asked, 2026-11-20); the mailman and `board.js` accept `approvedVia: "yolo"` for them as well as "board". Restrictions still apply: a held task stays in Pendientes, and a hold on the errors session keeps the errors proposed. Turning it on with tasks already pending asks first, because they go out at once. While it is on, the whole board looks "YOLO" (`html.yolo`; `styles/yolo.css` for the board, the end of `home.css` for the otters): warm orange palette, an energy bar running along the top, a glowing logo, the selected tab (fixed dark text and a white icon pill, so it reads in the dark theme too: with theme colours the icon went dark on dark and the owner could not see which page he was on) and primary buttons in a gold-orange gradient (buttons shake when hovered), cards that glow on hover, uppercase gradient page titles; the otters get spiky golden hair and a three-frame flame aura, both pixel art on the otter's own 0.25 grid with its dark outline (the first version, a smooth polygon and a blurred aura, looked out of place and the fringe hid the eyes, which start at y=2), plus rising sparks; the office gets speed lines and the Home notice a "power level" (1,000 per task sent by itself). The owner asked for a Dragon Ball look; the board is public, so it uses the genre's tropes on our own otters, never its characters. If the card was deleted from the board, the session is taken from `task-history.jsonl` (what deletion keeps): two tickets deleted one day came back returned the next and stayed in Pendientes because deletion lost the area.
- **Restrictions in code.** The owner: "if I need a restriction, I worry it won't be carried out". They used to be a line the orchestrator had to remember to copy into each delivery. Now they are records (`restrictions`, synced record by record) on tasks, epics or sessions; epic and session ones apply to whatever arrives later. `hold` blocks approving and sending on every path (buttons, `board.js` commands, the returned-task rule and the delivery itself, which checks again right before typing: all go through `holds.checkTask`); `note` lets it be sent but the code appends the text to every message. They expire at `until` (local time; a bare date means 00:00) or when lifted. Creating one sends whatever was in "Por enviar" back to Pendientes, and sessions that already had something covered get "Aviso del tablero: para la tarea…". Lifting it sends nothing: held work must be approved again, so nothing goes out by itself weeks later. Created in Tareas → Restricciones or by chat with the orchestrator (`board.js hold add`). "Pasar a Pendientes" is allowed on a held task: it sends nothing.

## Sessions reporting back

- **`done` refuses leftovers and missing causes.** It refuses while `pruebas/<KEY>/` or `.attachments/<KEY>/` remain (checked in the task's project and in the main project, where attachments always download), and on a returned task until `board.js cause` has been recorded after it came back (a cause from an earlier round does not count, or a task returned twice could close with the first round's cause).
- **Sessions tell the board with a command, not a message** (`done`, `partial`, `question`). Going through the orchestrator cost one of its turns per notice, and batches reach 35 tasks. "Done" means "the session finished", not "reviewed": the card is marked separately "Listo en Jira" when the reviewer closes it, which clears it. The owner's answer to a question is typed into the session by the board, because a stopped session does not notice by itself that it was answered. Would stop being valid if sessions stopped reporting reliably: "in progress" would mix everything again.

## Watchdog

- **A server process that looks for silent failures** (`src/features/watchdog.js`, no Claude, no quota). One day three failures went unnoticed: a Claude Code question the board did not detect (it drew spaces by moving the cursor), three start notices to the follow-up session (two simultaneous starts plus the notice on reopening it) and an order `board.js delivery` could not find because it was looked up by the D… id instead of the E…. The owner only found out by seeing them. Every 2 minutes it checks three things: a session `waiting` for more than 4 minutes with no question on the board, the same "Aviso del…" twice within 15 minutes in one conversation, and deliveries stuck in `typing` for more than 4 minutes. It warns once per problem: push, banner on Home and an "Aviso del tablero" to the board session so it looks for the cause. Would stop being valid if notices stopped starting with "Aviso del" or Claude Code stopped publishing the `waiting` state.

- **Board-down alert from another process.** The watchdog lives inside the server, so it cannot notice its own server hanging, and launchd's `KeepAlive` only restarts a process that exits, not one that hangs. The session host (a separate long-lived process) checks the board every minute and pushes to the phone after N minutes without an answer (`boardAliveMinutes`, default 5), again every hour, and when it recovers. A gap of more than 3 minutes between checks counts as the computer sleeping, so waking up does not raise an alert.

## Orchestrator

- **It no longer starts in order to watch.** When the host opens it (each morning's new conversation or on waking), the board types "Aviso del tablero: arranca la orquestadora" once so it reads its role, and it waits for the owner. It sleeps like area sessions.
- **It uses standalone commands.** Compound ones (`cd`, pipes, `node -e`, `$(…)`) trigger a permission prompt even with `Bash(*)` allowed. That is why `dispatches`, `hold` and `reply` exist: one command gives everything needed.
- **A dedicated "board" session** receives Chats requests about the board itself, so board improvements do not occupy the reporter. It is fixed like the reporter and orchestrator because otherwise it showed as "free" and could be picked as a task destination.

## Permissions filter

Every action of a session goes through the board. The owner asked for it to approve from the phone and so sessions stop halting on permission prompts nobody sees. It is a `PreToolUse` hook (`permission-hook.js`, in the root's `.claude/settings.local.json`) that asks the server (`src/sessions/permissions.js`). Three levels:

- **Passes by itself**: reading, searching and editing inside the repos, development commands and read-only git.
- **Passes only with a recorded order**: commit, push, merge and tag with a deploy approved for that session in the last 6 h. Without an order it waits in "Te esperan".
- **Jira writes only through `jira-write.js`.** The only ones that pass by themselves are `start`, `todo`, `block`, `assign` and `sprint` (assigning and moving to the sprint are the first steps of every task). Everything else asks: comments, mentions, edits, `create`, transitions to any other status, and every MCP write tool (`addOrEditJiraIssueComment`, `transitionJiraIssue`, `createJiraIssue`, `editJiraIssue`, `executeWrite`, `executeDestructive`, Confluence writes), matched by operation name on any `mcp__<server>__` prefix, plus `curl`/`wget` writes to the Jira site. Why: the filter used to protect only `addCommentToJiraIssue`, which the MCP server renamed, so comments and status changes ("Listo" included) passed silently; one day a session closed 67 tasks by moving them to the final status. Matching by operation name means a rename or a second connector does not silently open writes again. There is no "order" path for Jira writes any more.
- **Approving commands check their caller.** `approve-chat` (orchestrator or reporter), `hold add/release` (orchestrator) and `tidy-start/end` (orchestrator, or a session of that project for a project's own tidy, because the board sends those there) read `CLAUDE_CODE_SESSION_ID`, which Claude Code sets in every command a session runs (subagents inherit it), and look it up in `sessions.json`. Assigning that variable inside a command is protected, so a session cannot pass itself off as the orchestrator.
- **One `.env` read passes**: exactly a `grep '^DEV_LOGIN_CODE='` of the API project's local `.env` (the local login code), because the browser tester got stuck waiting on that prompt. Anything else touching `.env` keeps asking.
- **Asks only what the house rules cover**: reading or dumping `.env`, publishing to hosted artifacts, `rm -rf` of a root and `taskkill` of node or claude by name. Everything else passes, whatever it is (the owner: "auto-approve everything that is not in the rules"). Before, every unknown command was asked: it reached 90 manual approvals and 62 "always allow" rules, which were deleted.
- **On servers**, `ssh` passes if it only reads; it stops if the remote command changes something (writing outside `/tmp`, restarting services, installing packages, migrations or search-index rebuilds, console code that saves or deletes). `scp` stops only when uploading outside `/tmp`. Database reads over `ssh` + `mysql` pass if the SQL (or the `.sql` passed in) does not write, because the house rules only ask confirmation for database mutations and the follow-up session reads beta every hour. Commit and push in the board's own repo pass (it is always pushed without asking).
- It is a heuristic on the text: what goes inside `python -` or `node -e` is not inspected. The filter organises normal work; it is not a barrier against a session that wants to get round it. If the board does not answer, the hook classifies the action locally (`classify()`) and returns `ask` for protected actions, so Claude Code's own prompt appears; unprotected ones pass. Before, it stepped aside, and with `Bash(*)` allowed that let everything through while the board was down.

## Follow-up

- **A session summarises everyone's activity from the API request log**, which the owner used to ask for by hand. Since it follows everyone rather than one person: one summary per environment (beta hourly, production every two hours, within work hours) plus a closing one a minute after the workday ends for both, because the last stretch was being lost. Inside, activity is split by person. Why: the owner wants to know what each person does and which parts of the platform are used; following only one person left newcomers out.
- **People are a directory** (name and accounts). The session adds new teammates by itself (`board.js person-add`, only accounts on the company's mail domain). Accounts outside the directory get their own block with their address and role. Customers go in a "Customers" block: how many, what they use most and what errors they see; each customer who does something relevant (errors, writes, something odd, a new sign-up) is named with full name and address, and the rest are counted together. Why: the owner wants to know which user it was and recognises a name better than an address. The board is local; the data never leave it.
- **Scheduled summaries are fired by the server** (`src/features/followup-schedule.js`, "Aviso del tablero: toca el seguimiento…"), not by session crons: crons died with the session on restart and had to be deleted on pause. None fires while paused. "Pedir resumen ahora" works like Refresh (request recorded on the board, session woken with a `claude -p`) and does not move the scheduled window (`lastScheduled`). Frequency in `followUp.everyHours`. The first summary of the day per environment has no cap and covers the whole night.
- **Possible errors go to the errors session only by button.** The follow-up session records them separately (`board.js followup-error`) and the owner decides in the tab whether to send them; the board delivers them like tasks. So a failure someone hits while testing does not stay as a paragraph in a summary, and nothing goes to another session without the owner seeing it. A failure already sent that shows up again with new information is recorded as "Ampliación de <id>": once the session skipped it as a repeat and the owner had to send it by hand. Just in case, the latest summary has a button that sends it whole to the errors session.

## Sentry

- **Errors are sent to a session from the board.** The owner used to go to the VS Code tab and paste links. The server reads from the Sentry API the open error-level issues of the projects in `sentry` (the mobile apps stay out: they are not handled by this team's sessions). By default they go to the errors session; another can be picked. The board delivers them and the session reports with `sentry-result`, shown on the card with a notification. The token is not copied: it is read from the Sentry MCP server in `.mcp.json` (or `SENTRY_TOKEN` in `.env`), so there is one place to renew it. "Resuelto" and "Ignorar" change the state in Sentry; that is the only thing the board writes there, always by the owner's button. The list is cached in memory for a minute so Sentry is not called on every refresh.

## Dev servers and the tunnel

- **Local dev servers start with the first report of the day and stop at the end of the workday.** With the report and not at boot, because the owner also switches the computer on outside work. They stop within 10 minutes of the end of the workday, Monday to Friday; if he starts them later, they are left alone until the next day. Each project declares its `devServers` and the tab chooses which projects start by themselves; the AI assistant's server has `autoStart: false` because the session that needs it starts it.
- **Launched `detached`**, because on Windows Node puts its children in a job object that kills them with the parent, and every board restart took MySQL down (nothing in its log). They used to inherit a hidden console because, without one, a venv's `python.exe` opened a visible window; if that window comes back, it comes from here.
- **MySQL stops with `mysqladmin shutdown`**, because killing it leaves InnoDB corrupt; the rest by killing the process tree listening on its port, which covers the orphaned `php -S` the API project's dev server leaves.
- **Seeing the commanding machine's projects from the other: SSH tunnel, not `--host 0.0.0.0`.** Over the network the frontends load but login fails, for three reasons: they call the API on `localhost:8000`, which for the browser is its own machine; the API dev server only listens on `127.0.0.1`; and the API's local CORS only allows `localhost`/`127.0.0.1`. Opening it to the network would touch three projects. So in Servidores the standby machine opens an `ssh -N -L` for every project's dev-server ports to the commanding machine (`src/features/tunnel.js`), and there everything is `localhost`. It only works in that machine's browser, not on the phone; `/api/tunnel` is not forwarded, and the tunnel closes if that machine takes command, because it would occupy its own projects' ports.
- **Compressed (`ssh -C`).** A dev Nuxt page sends about 48 MB per admin-panel load and the machines move about 4.4 MB/s between them; uncompressed it took 17 s, with `-C` 5 s. A direct TCP relay over Tailscale barely gained (12.5 s): the bottleneck is bandwidth, not SSH.
- **The standby machine keeps its dev servers stopped** (owner's order): it does not start them, stops them if someone raises them and refuses "Arrancar", because once the PC's servers were holding the tunnel's ports and a test measured the PC's own admin panel by mistake. Stopping never kills the board itself or the tunnel's ssh, which listen on those ports.
- **The tunnel died with every PC board restart.** The `ssh` was a direct child of the server and Windows' job object killed it with the parent; since the board restarts on every commit to this repo, the tunnel "expired" every few minutes on busy days. It is now launched like the dev servers (hidden `Start-Process` from PowerShell), outside the job object, and the stored pid is the `ssh.exe`'s, not the wrapping `cmd.exe`'s: with the wrapper's pid, the sweep that keeps the standby's servers stopped saw the ports held by a foreign process and killed the tunnel minutes later.
- **Trap**: Windows' SSH server kills everything a session started when it closes, so restarting the PC's board over SSH has to launch it outside that session (`Invoke-CimMethod Win32_Process Create`); once it left the board down. SSH works both ways (Windows OpenSSH Server, firewall open only to Tailscale).

## Work schedule and after-hours mode

- **One configurable schedule** (Ajustes → Horario; default 07:30–18:30, weekdays) in one place (`src/core/hours.js`, `config.workSchedule`). It drives start-up and rotation of fixed sessions, Jira watching, follow-ups, stopping dev servers, the daily's time (`workSchedule.daily`) and the after-hours expiry. Before, each piece had its time hard-coded and changing the workday meant touching six files. It is different from the Mac's schedule, which only says when it is awake; the card warns if it does not cover the workday.
- **After-hours mode ("Activarlo todo") turns itself off.** Switched on in the early morning of a weekday (before the workday), it goes off when the workday starts and the normal schedule takes over. Switched on at any other time (evening, during the day to carry on later, weekend), it goes off at 00:00 and the commanding machine puts everything to sleep as with "Terminar y dormir todo" (owner's order: if he forgets it, it must not run all night). It used not to expire: once switched on at 06:09, it was still on mid-morning and nothing would have slept at the end of the day.

## Plan quota

- **The plan quota comes from an unofficial endpoint.** The documented one only reaches the status line (`statusLine`, `rate_limits`), and the VS Code extension does not run it: tried, it wrote nothing. So the server asks `api.anthropic.com/api/oauth/usage`, the same service `/usage` uses, with the `/login` token; the token is read locally and never printed, and the call spends no quota. The owner chose it knowing it may break without notice: then the header keeps the last value, dimmed, with its date.
- **The endpoint rate-limits hard.** With both machines asking every 3 minutes it returned `429` with a `retry-after` of about 45 minutes and, since it asked again earlier, never unblocked (for a day the header showed the previous day's value as current). It now asks every 10 minutes and respects `retry-after`.
- **Only the login works**: with the long-lived token it always returns 429, and on the Mac the board cannot read the login from the keychain (`security -w` is empty from its processes). So the machine with a live login asks, the commanding machine takes the value from the other (`/api/cluster/quota`), and if neither has it, it reads the `anthropic-ratelimit-unified-*` headers of a minimal `/v1/messages` call (one Haiku token every 10 minutes; the 5-hour one only appears sometimes).

## Deploys

- **Deploy state is read, not guessed.** Each back-end environment shows two phases with progress bars (Actions by steps, CodeDeploy by instance), because with one line it was not visible that CodeDeploy runs after Actions. It reads the last GitHub Actions workflow and, where configured, the group's last CodeDeploy deployment (`deployProjects`), with `gh` and `aws` already logged in on the machine: no quota. A back end is not deployed until CodeDeploy finishes; if Actions finished but the last CodeDeploy is older, it shows "Esperando a CodeDeploy". A "Despliegues" push arrives on finish or failure.

## Notifications

- **Push to phone and desktop with the text encrypted.** A push has to go through Google's or Apple's service, so the text is encrypted (aes128gcm). At first it went out empty and the device asked the board for the reason, but with the phone asleep that request failed or took over 10 minutes and a generic "Hay novedades" appeared; a subscription without keys still works that way until the page registers it again. It only notifies new cards in Pendientes and sessions that ask or stop halfway: the owner chose that. Switched per device with the bell in the header. At most one notification per minute per type: 30 cards at once give one notification. `data/push-vapid.json` holds the signing private key: secret.
- **Quiet signals, not alerts.** A sent task with no news from its session for 3 hours shows "Sin noticias desde hace N h"; next to the last check, "Envíos activos" with a green dot, or in red "N envíos sin entregar" (links to Por enviar). In the report, rows assigned to the owner carry a mark on the left. The owner asked that none of this be intrusive.

## Page and UI

- **Chats are the live sessions, not a chat.** It used to be a chat with messages, voice notes (Whisper) and spoken replies (Piper). The owner dropped it as soon as he could see and type into live sessions from the host: it is the same conversation as in VS Code, with its thinking and actions, and Esc to stop. The server keeps the message and voice routes and the `message`/`answer-message` commands in case they are needed again. A chat would make sense again if he needed to talk to a session that does not live in the host. A chat-like "reading view" to copy text more easily was proposed again and rejected: he wants to see the thinking. Copying was solved in the terminal itself (drag and Ctrl/Cmd+C, and a "Copiar" button with the last reply).
- **Attachments in Chats** are uploaded to a per-day folder of the commanding machine, mentioned with @, and deleted after 7 days. A chat of another project uploads to `<project folder>/.tablero/hablar/<day>/` (kept out of git through `.git/info/exclude`), with an absolute path. Before, everything landed in the main project, so a client project's personal data (screenshots of operations) ended up in the wrong repo. If the project has no folder on that machine the upload is refused rather than falling back to the main project.
- **Mobile: a bottom bar with Hoy, Tareas, Chats and Más**, not a row of tabs. With 17 tabs in a horizontal strip the owner could not find anything on the phone. "Hoy" holds the open sessions, Home's four shortcuts (Pendientes, Te esperan, En curso, Hechas), whatever needs him (Te esperan, A medias, Pendientes, possible errors) and the report below; empty sections are hidden. The red count on each button is only what awaits his decision. The desktop does not change: everything fits there.
- **Desktop side menu always narrow, Slack style** (icon with the name below, no collapse button), groups My day, Sessions, Fix and deliver, Settings; Learning and context tidy together under "Contexto"; the project picker as a square with an initial at the top of the menu.
- **Home on desktop shows the state of open sessions.** Claude Code only gives "busy" or "idle" per session (`~/.claude/sessions`). "Blocked" is set by the board: an idle session with a task waiting for the owner, halfway, or sent more than 5 minutes ago without news. A session whose turn ended but has a subagent running (tester, reviewer) counts as working, the owner's criterion: Claude Code marks it "idle" and it showed as "stopped without notice". A subagent counts as alive if its transcript (`<conversation>/subagents/`) does not end in `end_turn` and was written in the last 30 minutes, or if a command it started in the background is still alive (a tester once closed its turn with the test still running). The main session's background commands (a dev server) do not count, because they live for hours without being work: Claude Code's "shell" state shows as free ("Esperando · con proceso de fondo"), since a session once showed busy after closing its task only because of a local dev server it had started. Such a session does not sleep by itself and does not let the host restart, because stopping it would kill that process. On the phone it is a collapsible strip above Hoy, because the report fills that screen. Follow-up, reporter and orchestrator do not count as area sessions.
- **Tasks on desktop as a kanban.** Pendientes keeps the per-epic blocks with their session and "Hacer las N", because sending a whole epic at once is what the owner uses most. To try such changes without sending anything to real sessions: a separate board with `TOWER_DATA` and `TOWER_PORT` pointing to another folder and port.
- **Automatic smoke test after every update.** On starting with an untested commit the board opens each view in a headless Chrome (desktop and mobile, never Chats, so no session gets resized) and, on errors, tells the board session, not the owner (`src/server/smoke.js`, `data/smoke.json`). Three bugs slipped through on the day it was added that this would have caught.
- **Settings live in a modal, not in the sidebar**, in three groups: Tablero (Proyectos, Avisos, Servidores), Equipos (Ordenadores, Horario, Cuenta de Claude) and Tú (Notificaciones, Permisos, Apariencia); the gear at the foot of the rail, «Ajustes» in Más on the phone. They are visited rarely, and taking them out leaves the rail for the daily work. It works like Slack's or Claude Desktop's settings: sections on the left, the pane on the right, full screen on the phone with the sections as a row of chips. Every pane is built from the same pieces (`components/settings-ui.js`: titled groups of rows with the label and its explanation on the left and the control on the right, switches, segmented choices), so they read alike. The views are painted into `#settings-body` on every render (`components/settings.js`); `state.settings` holds the open section, `switchView()` to one of those ids opens the modal, so old links, pushes and `?tab=machines` still land there. Typing inside the modal defers the repaint like typing in the page. Its children must not shrink (`flex-shrink: 0`), or the server lists get squashed inside the scrolling body. Ordenadores was split because it mixed three things (who commands, the workday, the Claude token); reminders left Proyectos because they sat at the bottom of a long list; the always-allowed permissions left Te esperan, where nobody looked for them; the notifications bell left the activity header for a pane that also chooses what to notify about.
- **What to be notified about is chosen per device** (`muted` on each push subscription, `/api/push/prefs`), because the phone may want everything and the Mac only the urgent things. It survives re-subscribing: a renewed subscription of the same device keeps the list.
- **Appearance (Settings → Apariencia): light or dark theme, saved per browser** (`localStorage` `tower-theme`), because the phone and the Mac may want different ones and it does not touch the shared data. System, light or dark over the existing `data-theme` tokens, set by an inline script in the page head so it does not flash. A configurable cast of characters was tried and dropped: the owner preferred a better otter. The otter is drawn at four times the grid resolution with a thin dark outline and shading, split into layers (`LAYERS` in `src/page/components/nutria.js`: tail, body, feet, head; colours still from CSS classes so fur, outfits and hats per session keep working). The layers animate on their own (breathing torso, tail sway, head and eyes looking, typing arms, cheering, squash and stretch on hops, dozing) because moving the whole sprite looked stiff, and the old one-unit arm jump left the paws behind. Animations live on inner groups, never on the `svg`, so `.mirror` keeps its flip; each painted otter gets its own delay (`--nd`) so a room does not breathe in step. Arms and eyes use half steps with the same outline. Outfits and hats are drawn the same way and clipped to the body and head shapes, so they no longer stick out as blocks; sweaters and hoodies colour the sleeves (`data-outfit`). Props stay on the 17×15 grid.
- **Language: Spanish or English, per browser** (`localStorage` `tower-lang`, Settings → Apariencia). The Spanish text is the key (`t()` / `tn()` in `src/page/lib/i18n.js`, English in `src/page/i18n/en-<area>.js`), so the code still reads in Spanish and a missing entry falls back to Spanish instead of showing a key. Changing language reloads the page, which lets module-level labels call `t()` once. Static texts in `index.html` carry `data-t`, `data-t-title` or `data-t-aria`. Only the board's own texts are translated: what sessions, Jira and the server write stays as written. Otters are painted from the Spanish names so they look the same in both languages.
- **Home layout: the otter office or the classic columns and cards** (`tower-home`), because the office is nicer to look at but the columns read faster; the columns view keeps the counters, the three session columns, the board sessions as chips and the permissions with their command and ✓ ✕. On the phone the three columns become one «Sesiones abiertas» dropdown (open by default when one is blocked, remembered per tab), as it was before the office, because three columns don't fit at 390 px.
- **Home shows how long things have waited.** Queued and blocked otters carry `wait-some` (5 min) and `wait-long` (15 min): they wave and hop faster and fret, and a minutes badge appears, because two waits that looked the same hid which one to answer first. Tu mesa lists what each permission asks (the command, not just «Do you want to proceed?») next to its ✓ ✕, since the tooltip never shows on the phone. On the phone, rooms with something in them go first, empty rooms shrink, and the ✓ ✕ buttons are finger-sized.
- **The page compares state without the session-read time, and does not repaint with a select or focused field inside the content**: that time changes on every poll and repainting closed selects and the open history. The sidebar search counted too, since it keeps focus after searching: new permissions did not show until clicking elsewhere.

## Daily summary

- **The board drafts the owner's daily notes.** He writes himself in Slack "things to mention at the daily" in his own voice. The board drafts it from the tasks he sent that day (closed ones stay in `data/task-history.jsonl`, because the board deletes them), his commits with that day's author date and the Sentry and follow-up errors he sent to fix, imitating a daily written by him (`dailyStyle`; code in `src/features/daily.js`). Using his Jira tickets that changed state that day was tried and pulled in work from earlier days: reviewers and sessions move tickets later. A `claude -p` drafts it on its own at the daily time of the workday over that same day; if that day it could not (some days, especially Fridays, the computer is off by mid-afternoon), next morning over the last working day, since Jira and git keep it. Its own tab shows the last working day and today, grouped by area with what, where and how. Each day also has a button to draft it again (removed on 2026-11-13, back on 2026-11-18 because the owner needed to redo a draft written before the day's work was in); only the computer in command drafts.

## Learning tab

- **Does the context reduce returns from review?** Everything is in rates per delivery, never absolute counts: task volume tripled in two months because the team uses AI in more and more flows, and that says nothing about learning. A return is a move out of review to To do, Blocked or In progress made by someone else; the owner's own moves do not count. A domain's date is the first one in its history, because the context repo's git history starts after most of them. The comparison is per session area (its epics in `sessions.json`): last 4 weeks against the 4 before and against what happened before its first domain. Comparing per epic was rejected, because a large epic is cited by many domains (one by 13) and almost all epics were born together with their context, so there was no "before". The cause of each return (already written or new) is recorded by the sessions with `board.js cause`: the only direct measure of whether the context is used. Jira data is read in a separate process every 3 hours, with no quota. The numbers do not prove causation: models and volume changed in the same period.

## Context tidy

- **Any session runs the tidy when the last pass is older than 7 days**, as the main project's agent rules say, and it merges, splits or deletes domains without asking (it says what it did). The board button is another way to launch it, and only enables with everything clean: it is blocked while there are tasks pending, to send, in a session, waiting or halfway, because reordering the context while other sessions write in it would overwrite their changes. Deploys do not block: they do not write context, and one that was sent and never answered kept the button blocked forever. The server checks the blocks again on press, not only the page. From the button the board tells the orchestrator, which delegates to a subagent that reads the tidy command (it cannot be launched as a skill from the model) and applies the changes, then closes with a one-line summary.

## Several projects

The owner also wants to run his own projects and other clients', with or without Jira, maybe with other agents besides Claude. He chose one board with several projects, not one board per project: with several, each would think it owns the Mac, the handover and the quota. What is shared is the person and their machines (handover, shutdown, quota, workday, Chats, mailman, the board session); what is per project is tasks and their source, areas, reviewer, deploys, Sentry, follow-up, context and credentials. Fixed sessions (reporter, orchestrator, follow-up) are one per project (`projectRoles`), so two clients never share a conversation.

- **Membership without migrating data.** A session belongs to the project whose folder contains it (deepest root wins; outside all, it is not shown). A record without `project` belongs to the project of its Jira key or else the first one (its id derived from the company name so both machines get the same one when upgrading the old format by themselves). A task never goes to another project's area: `holds.checkTask` blocks it. Trap: on macOS a folder has two names (`/var` and `/private/var`); `projectOfPath` compares real paths.
- **Modules.** Jira and its report, follow-up, Sentry, deploys, dev servers, daily and context tidy exist only if the project configures them, and the page hides what it lacks. The method lines the board appends to each delivery (reviewer, tester, `board.js cause`) belong to the main project (`messages`); others get only neutral text, and projects without Jira a basic `/soy` that explains the protocol, because their agent rules do not. Another project's context tidy is received by a session of that project, told to follow its own agent rules and never another's.
- **Manual tasks** ("Nueva tarea" or `board.js task-new`): own key `<PREFIX>-<n>` (`taskPrefix` or the id in capitals, never a Jira one). Trap: `taskPrefix` must change on both machines at once or keys will not match.
- **Projects panel** (Settings → Projects, so `board.config.json` is not edited by hand on each machine): the shared part (`projectDefs`) syncs record by record; the folder goes in each machine's `data/projects-local.json` because the path differs, and credentials in `.env.<id>`, which the panel writes and never shows. Deleting leaves a tombstone and is refused with open tasks. The top-bar project picker filters the whole board.
- **Agent**: what is Claude Code-specific lives in `src/agents/claude.js` and each project may set `agent`; transcript reading, permissions and quota are still tied to Claude and will have to move into the adapter when a second agent arrives.
- **Conversations of every project synced both ways** (owner's order): before, only the main project's hosted ones travelled, and what was said in VS Code on the other machine did not arrive. Each side offers its VS Code conversations of the last 14 days and whoever pulls them puts them in its project's folder (transcript folders are named differently on Mac and PC). Neither side touches a conversation open in its own VS Code, because replacing it while the session writes would lose lines, nor pulls one whose copy is already ahead (hash of the tail). Each project's memory travels through `/api/cluster/memory/<id>`. The host starts each conversation in its project's folder, because `--resume` looks for it there. Trap: the first time in a folder Claude Code asks about trust with "No, exit" as default, and the host's Enter closed the session; it now moves to "Yes".
- **Still missing**: Jira watch, report, follow-up, deploys and Sentry walking every project with its credentials (today only the first), and the mailman delivering to `projectRoles` roles.

## Access from outside

- **Tailscale only, inside the owner's tailnet**: `tailscale serve`, never `funnel` or a public tunnel. The board has no password and deploys to production.
- The server rejects any `Host` that is not local or listed in `data/board-hosts.txt`.
- `serve` only answers by **name**; by IP it returns "404 page not found".
- It uses `https` because Android only installs a secure site as an app. Turning it on put the tailnet name in the public certificate transparency log; the owner accepted that. The first access is slow while the certificate is issued.
- "Abrir en VS Code" does nothing from the phone: it opens VS Code on the device where it is pressed.

## Code and repository

- **Every change to this repo is committed and pushed to `main` as soon as it is tested**, without asking: the exception to the owner's no-commit rule. The workspace folder holds config, `.env`, `data/` and the launchers `install.js` writes. The installer also renders the slash commands from `templates/commands/`: those are changed here and reinstalled, never by hand.
- **Automated tests with `npm test`**: `node:test`, no dependencies, in `test/` and in CI. They mostly cover what broke most (schedule, merge between machines, permissions, tunnel, rotation, quota). Each file sets up a temporary workspace (`TOWER_WORKSPACE`, `TOWER_DATA` and `HOME` in tmp), so they never touch real data or the network. The whole server is deliberately not started in tests: on the Mac it would reinstall the launchd agent and its power timer could call the real `pmset`. When a test fails after a change, first ask whether the new behaviour is the intended one: tests describe what it does today, not what it should.
- **`data/` logs capped at 1 MB**, because they grew forever (`hook.log` reached 640 KB); code in `src/core/logfile.js`. Traps: launchd keeps `serve.log` open and it cannot be renamed, so it is copied and emptied on start; `task-history.jsonl` does not rotate because it is data (the daily reads it).
- **Moving files.** The launchers the installer writes in each workspace point by absolute path to `src/cli.js` and `bin/*` (that is why `src/cli.js` is still the entry point although commands live in `src/commands/`, one per topic), and the other machine's board pulls and restarts itself every 3 minutes with whatever is on `main`: what is pushed must work whole, and those files cannot move without reinstalling on both machines. A running host does not break when its modules move (Node keeps already-resolved `require`s) and restarts by itself when sessions are idle. To check that a reorganisation changes nothing visible, comparing the computed styles of every element in every view, at three widths, before and after, worked.

## Traps

- **A key that does not exist in Jira breaks the attachments query for every card.** Test cards use a key without a number.
- **A conversation created with the CLI does not appear in VS Code** unless created with the extension's entry point, and **it keeps the model it was created with**: two sessions worked on Haiku and one on Sonnet until the model was pinned.
- **Opening a `vscode://` link from a Claude process does nothing** if it inherits the variable that makes VS Code start as node; remove it from the environment.
- **Child sessions that save nothing.** A `claude` launched from another session inherits `CLAUDE_CODE_*` variables (`CLAUDE_CODE_CHILD_SESSION`, among others) and does not write its conversation: later `--resume` says "No conversation found". The host and its sessions start with `cleanEnv()`, as do wake-ups with `claude -p`.
- **Folder trust is per exact path.** On Windows a drive-letter path in upper case and the same in lower case with forward slashes are different projects for Claude Code. Starting with the other spelling asked again, and the automatic answer ended in "No, exit". The host uses the same spelling as VS Code.
- **`jira-window.js` shows the current assignee**, not the one at the time of the event: an "unassigned" ticket can appear already assigned if a session took it.

## Moving the server to Rust (branch `rust`)

- **Why.** The owner wants the board to take as little memory as possible so sessions, servers and test browsers have more room. Measured on 2026-11-23: the Node processes of the board take about 310 MB; the first Rust step serving the same page takes about 3 MB. The page stays in JavaScript: it runs in the browser.
- **Step by step, never a big switch.** A Rust server (`rust/`, binary `tower`) sits on the public port (4747), checks the host like Node did, serves the page, the service worker, the manifest, the icons and xterm, and forwards everything else, terminal WebSockets included, to Node on an internal port (`TOWER_LISTEN_PORT` for Node, `TOWER_NODE_PORT` for Rust, public port + 10 by default). Node keeps checking the origin and keeps `TOWER_PORT` as the public port, so its own calls to `BASE_URL` go through Rust. Each route or timer moved to Rust is removed from Node; when nothing is left, Node goes. Both read the same SQLite file (`documents` table, one JSON document per key, `BEGIN IMMEDIATE` to write), so data and API do not change.
- **The service worker lives in `src/page/sw.js`** so both servers serve the same file instead of two copies of the text.
- **Done on 2026-11-23: the whole server, CLI, hooks and session host are one Rust binary** (`rust/`, `tower`), synchronous with threads, data as `serde_json::Value`, JSON printed exactly like `JSON.stringify` (stored texts are compared and merged between machines). Rules and layout for anyone changing it: `rust/PORTING.md`. Checked before switching: the 42 stored documents of the real board round-trip byte for byte; with a copy of the real data, `/api/state` (334 KB) and every GET the page makes are identical between Node and Rust; a real Claude session runs in the Rust host (startup dialog answered, typing from the web terminal, delivery through `/input`); the Rust permission hook answers the real board (11 ms against 45 ms); a test push reached the three devices. Memory: about 39 MB (server and host) against about 171 MB. Known small differences, accepted by the owner because nothing he uses changes: text cuts count characters instead of UTF-16 units, the terminal buffer is measured in bytes, network error texts, invalid JSON in CLI commands prints an error instead of a stack trace, a too-large body gets 413 instead of a dropped connection, periodic jobs never overlap.
- **The PC moved the same day.** Rust there needs the Visual Studio Build Tools (C++ workload, MSVC linker) besides rustup, so the board can rebuild itself after a pull. One Windows-only fix came out of testing a real session: ConPTY (opened by portable-pty with "inherit cursor") asks for the cursor position (`ESC[6n`) and waits for the answer before the program shows anything; node-pty did not need it. The Rust host answers `ESC[1;1R` on Windows.
- **Switching and going back are the installer**: `node install.js <workspace> --rust` writes launchers that call the binary (small Node shims, so every `node .../board.js` command in commands and context keeps working); without `--rust` they call the JS again, which stays in the repo until the PC moves too. The JS code is not deleted yet for that reason.
- **launchd and the port**: `tower serve` outside launchd rewrites the agent and checks it really runs (kickstart if not); on start it waits up to 30 s for the port while the previous server exits. Both were found when switching: the first bootstrap left the agent loaded but stopped for a minute.
